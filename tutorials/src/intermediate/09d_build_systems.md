# Intermediate 9d — Build-system integration: Makefile, CMake, Meson

> **Learning goal**: integrate vāṇī into an existing C/C++ build pipeline using
> `vanic emit --backend=c` to generate portable C, then compile and link that C
> with Makefile, CMake, or Meson (including Ninja-backend CMake/Meson projects).

> **Prerequisite**: [FFI: `extern "C"` + `--link-with`](09_ffi.md)

---

## How the integration works

vāṇī has two compilation modes:

| Mode | Command | Use case |
|------|---------|----------|
| Build native binary directly | `vanic build src/main.vani -o hello` | standalone vāṇī project |
| Emit C for external toolchain | `vanic emit src/main.vani --backend=c -o build/main.c` | mixed C+vāṇī; embedded BSP; audit trail |

The second mode is the integration point. `vanic emit` type-checks the program,
applies SMT verification, and writes readable C to a file. Your existing build
system then compiles and links that C exactly like any other `.c` source.

When the entry file uses `use "other.vani"` imports, vāṇī follows them
transitively and includes all modules in the emitted output — so you get one
`.c` file per entry point, not one per source file.

## Example project layout

```
myproject/
├── vani.toml          ← manifest (needed for vanic check / vanic add)
├── src/
│   ├── main.vani      ← entry point
│   └── math.vani      ← imported module
├── c_helper.c         ← existing C code (optional)
└── build/             ← generated output (git-ignored)
```

`vani.toml`:

```toml
[package]
name  = "myproject"
entry = "src/main.vani"
```

`src/math.vani`:

```vani
intent "Math helpers.";

module math {
  pub fn square(n: i64) -> i64 { return n * n; }
  pub fn cube(n: i64)   -> i64 { return n * n * n; }
}
```

`src/main.vani`:

```vani
intent "Multi-file demo.";

use "math.vani";
use math::square;
use math::cube;

fn main() -> i64 {
  print square(4);   // 16
  print cube(3);     // 27
  return 0;
}
```

Everything below shows how to build this project with each tool.

## Makefile

### A — Pure vāṇī project

A thin wrapper that lets `make run / check / build` drive the native vāṇī
pipeline. Good when you just want familiar Make targets without a full CMake
setup.

```makefile
VANIC ?= vanic
SRC    = src/main.vani
BIN    = build/myproject

.PHONY: run check build clean

run: $(SRC)
	$(VANIC) run $(SRC)

check: $(SRC)
	$(VANIC) check $(SRC)

build: $(BIN)

$(BIN): $(SRC)
	mkdir -p build
	$(VANIC) build $(SRC) -o $(BIN)

clean:
	rm -rf build/
```

### B — Mixed C + vāṇī project (emit → compile → link)

Use this when you need to link vāṇī code with existing C objects, or when the
target platform has no LLVM toolchain and you rely on a bare C compiler.

```makefile
VANIC ?= vanic
CC    ?= cc
CFLAGS = -O2 -Wall

SRC      = src/main.vani
VANI_C   = build/main_vani.c   # generated by vanic
VANI_OBJ = build/main_vani.o
C_OBJ    = build/c_helper.o
BIN      = build/myproject

.PHONY: run check build clean

run: build
	./$(BIN)

check:
	$(VANIC) check $(SRC)

build: $(BIN)

# Step 1 — vāṇī → C
$(VANI_C): $(SRC) src/math.vani
	mkdir -p build
	$(VANIC) emit $(SRC) --backend=c -o $(VANI_C)

# Step 2 — C → object
$(VANI_OBJ): $(VANI_C)
	$(CC) $(CFLAGS) -c $(VANI_C) -o $(VANI_OBJ)

# Step 3 — compile the C helper
$(C_OBJ): c_helper.c
	$(CC) $(CFLAGS) -c c_helper.c -o $(C_OBJ)

# Step 4 — link everything
$(BIN): $(VANI_OBJ) $(C_OBJ)
	$(CC) $(VANI_OBJ) $(C_OBJ) -o $(BIN)

clean:
	rm -rf build/
```

**Dependency tracking tip**: list all `.vani` source files on the `$(VANI_C)`
target line (`src/main.vani src/math.vani ...`) so Make re-emits when any
module changes. Alternatively, use `$(wildcard src/*.vani)`.

```makefile
VANI_SRCS = $(wildcard src/*.vani)

$(VANI_C): $(VANI_SRCS)
	mkdir -p build
	$(VANIC) emit src/main.vani --backend=c -o $(VANI_C)
```

## CMake

### Single-entry integration

```cmake
cmake_minimum_required(VERSION 3.20)
project(myproject LANGUAGES C)

# Locate the vanic binary
find_program(VANIC vanic REQUIRED
  DOC "vāṇī compiler CLI (install via cargo install vanic)")

set(VANI_ENTRY  ${CMAKE_SOURCE_DIR}/src/main.vani)
set(VANI_C_OUT  ${CMAKE_BINARY_DIR}/main_vani.c)

# Glob all .vani files so re-emit fires when any module changes
file(GLOB_RECURSE VANI_SRCS ${CMAKE_SOURCE_DIR}/src/*.vani)

# Step 1 — emit C from vāṇī entry point
add_custom_command(
  OUTPUT  ${VANI_C_OUT}
  COMMAND ${VANIC} emit ${VANI_ENTRY} --backend=c -o ${VANI_C_OUT}
  DEPENDS ${VANI_SRCS}
  COMMENT "vāṇī → C: ${VANI_ENTRY}"
  VERBATIM
)

# Step 2 — compile the generated C as a static library
add_library(myproject_vani STATIC ${VANI_C_OUT})
target_compile_options(myproject_vani PRIVATE -O2)

# Step 3 — your C executable or library links against it
add_executable(myproject c_helper.c)
target_link_libraries(myproject PRIVATE myproject_vani)
```

**Build:**

```bash
cmake -B build
cmake --build build
./build/myproject
```

### With Ninja backend (faster rebuilds)

Ninja is a build-execution engine; CMake writes the `.ninja` files for you.
No changes to `CMakeLists.txt` — just pass `-G Ninja`:

```bash
cmake -B build -G Ninja
ninja -C build
```

Everything else is identical. CMake's `add_custom_command` teaches Ninja about
the vāṇī → C dependency edge, so a change to any `.vani` file triggers
re-emit + recompile automatically.

### Calling vāṇī functions from C

When `c_helper.c` needs to call a function defined in vāṇī, add
`#[no_mangle]` to the vāṇī side and declare it `extern` in C:

`src/main.vani` — expose one function to C:

```vani
#[no_mangle]
pub fn add(a: i64, b: i64) -> i64 {
  return a + b;
}

fn main() -> i64 { return 0; }
```

`c_helper.c` — call it:

```c
#include <stdio.h>

extern long long add(long long a, long long b);

int main(void) {
    printf("%lld\n", add(3, 4));   // 7
    return 0;
}
```

`CMakeLists.txt` — the `add_executable` uses `c_helper.c` as the C entry point
and links the vāṇī library; remove vāṇī's `main` or rename it:

```cmake
add_executable(myproject c_helper.c)
target_link_libraries(myproject PRIVATE myproject_vani)
```

## Meson

Meson is common in embedded Linux projects (Yocto, OpenEmbedded) and produces
Ninja build files by default.

`meson.build`:

```meson
project('myproject', 'c',
  default_options: ['c_std=c11', 'optimization=2'])

vanic = find_program('vanic', required: true)

# Emit vāṇī → C
vani_c = custom_target('vani_emit',
  input:   'src/main.vani',
  output:  'main_vani.c',
  command: [vanic, 'emit', '@INPUT@', '--backend=c', '-o', '@OUTPUT@'],
  depend_files: files('src/math.vani'),   # re-emit when modules change
)

# Compile to a static library
vani_lib = static_library('myproject_vani', vani_c)

# Link with the C side
executable('myproject',
  sources:      ['c_helper.c'],
  link_with:    vani_lib,
)
```

**Build:**

```bash
meson setup build
ninja -C build          # Meson always uses Ninja by default
./build/myproject
```

**Cross-compilation** (e.g. AArch64 on an x86 host): pass a Meson cross-file
alongside `--cross-file` and set the `CC` / `VANIC` entries in it. vāṇī's C
backend output is portable C11 and compiles cleanly under any AArch64 GCC or
Clang cross-toolchain.

## Checking without emitting (CI usage)

All three build systems can call `vanic check` as a pre-build validation step
that type-checks and runs SMT proofs without producing any output — useful in
CI to get fast feedback before the slower emit + compile step.

**Makefile:**

```makefile
.PHONY: lint
lint:
	$(VANIC) check src/main.vani
```

**CMake:**

```cmake
add_custom_target(vani_check
  COMMAND ${VANIC} check ${VANI_ENTRY}
  WORKING_DIRECTORY ${CMAKE_SOURCE_DIR}
  COMMENT "vāṇī type-check + SMT"
)
```

**Meson:**

```meson
run_target('check',
  command: [vanic, 'check', 'src/main.vani'],
)
# meson setup build && ninja -C build check
```

## Which approach to choose

| Situation | Recommended approach |
|-----------|---------------------|
| Pure vāṇī project, simple needs | `vanic build` directly; Makefile wrapper for familiar targets |
| New project with C helpers | CMake + `add_custom_command` |
| Embedded Linux / Yocto recipe | Meson `custom_target` |
| Existing large C/C++ CMake project | Add `add_custom_command` + `add_library` to existing `CMakeLists.txt` |
| Bare-metal with proprietary BSP toolchain | Makefile B — emit C, then compile with the BSP's own `cc` |
| Need fast incremental builds | Any approach with Ninja backend (`-G Ninja` for CMake, default for Meson) |

> **Note on raw Ninja**: `.ninja` files are generated by CMake or Meson — you
> do not write them by hand. Choose CMake or Meson as the frontend; Ninja
> handles fast parallel execution behind the scenes.
