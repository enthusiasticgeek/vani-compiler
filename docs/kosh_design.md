# Kosh package manager — design notes

**Status**: scaffolding draft, 2026-06-08. Pre-decision on registry-
hosting; this doc captures the design choices that are
registry-agnostic so the implementation can move when the hosting
choice lands.

`Kosh` = कोश ("treasure / repository"). The package manager for
vāṇी, queued as Arc 9 (a/b/e/f) in [TODO.md](../TODO.md).

## Status today (2026-06-08)

What ships:
- `vani.toml` manifest with `[package]` (name, entry) +
  `[deps]` path-style (`name = { path = "../lib-dir" }`).
- Manifest parser at [`src/manifest.rs`](../src/manifest.rs).
- `find_manifest` parent-walk; `[package].entry` resolution.
- Visibility tiers: `pub(kosh)` already in the language.

What doesn't:
- Registry-hosted deps. Path deps require the user to fetch
  the source manually.
- Version constraints. No `version = "^1.0.0"` syntax.
- Lockfile. No `vani.lock`.
- `vanic vendor` / `vanic add` / `vanic publish`.

## Why this doc exists

The registry-hosting choice (git-based / http-served / IPFS /
custom protocol) influences enough of the manifest format
that committing to partial code before the choice is wasteful.
This doc captures decisions that don't depend on the registry
so the implementation can move in clean chunks when the choice
is made.

## Decisions captured (registry-agnostic)

### 1. Version constraint syntax — semver-style, Cargo-compatible

`[deps]` entries gain an optional `version` key:

```toml
[deps]
foo = { path = "../foo-lib" }                    # path-only (today)
bar = { version = "^1.2.3" }                     # registry-only (Kosh future)
baz = { path = "../baz", version = "^0.4" }      # path + version-pin
```

Constraint shapes (Cargo's notation):
- `"1.2.3"` — exact / SemVer-compatible (`^1.2.3` shorthand).
- `"^1.2.3"` — explicit caret. Compatible with `1.x.y` `(x>=2)`.
- `"~1.2.3"` — tilde. Compatible with `1.2.x` `(x>=3)`.
- `">=1.2.3, <2.0.0"` — range.

`path` and `version` are independent: when both are set, the
build resolves `path` (no registry lookup) but VERIFIES the
loaded `vani.toml` advertises a `version` matching the
constraint. Mismatch → diagnostic.

### 2. `[package]` gains a `version` field

```toml
[package]
name = "foo"
version = "0.1.0"
entry = "src/main.vani"
```

Required when the package will be published to a registry.
Optional otherwise; today defaults to `"0.0.0"` (sentinel for
"never published").

### 3. Lockfile format — `vani.lock`

Cargo.lock-style. Generated by `vanic build` / `vanic run`
when at least one registry dep exists. Path-deps-only
manifests don't need a lockfile (the path IS the lock).

```toml
# This file is automatically @generated by vanic.
# It is not intended for manual editing.
version = 1

[[package]]
name = "foo"
version = "1.2.3"
source = "registry+https://kosh.example.org/index"
checksum = "sha256:abc123..."
deps = ["bar 0.4.1"]

[[package]]
name = "bar"
version = "0.4.1"
source = "registry+https://kosh.example.org/index"
checksum = "sha256:def456..."
```

Source field formats:
- `"registry+<url>"` for Kosh-hosted deps.
- `"git+<url>?rev=<sha>"` for git deps (future).
- `"local"` for path deps (no checksum).

### 4. CLI surface

Commands that need to exist before launch:

| Command | Effect | Registry needed? |
|---|---|---|
| `vanic build` / `run` / `check` | existing | no |
| `vanic add <name>[@version]` | inserts into `[deps]` + resolves + updates lockfile | YES |
| `vanic remove <name>` | removes from `[deps]` + updates lockfile | no |
| `vanic vendor` | copies path-deps' sources into `vendor/` for offline builds | no |
| `vanic publish` | uploads current package to the registry | YES (write) |
| `vanic search <q>` | queries registry for packages | YES |

The `vanic vendor` command is the highest-value pre-launch
piece: it works today against path-deps and unlocks "offline-
reproducible build" without a registry.

### 5. `pub(kosh)` visibility — already shipped

The visibility tier is already in the language (commit 257).
Items marked `pub(kosh)` are visible within the same package
but NOT exported across the registry boundary. This composes
cleanly with the registry's "what crosses the package
boundary" decision — pub-without-qualifier is the export
surface.

## Registry decision — 2026-06-16 ✅ DECIDED

**Chosen: GitHub Pages sparse index + GitHub Release assets.**

Rationale: vāṇी has zero external users today. The goal is a
free, zero-infrastructure setup that scales to real adoption
without a format change. The Cargo sparse registry (RFC 2789)
pattern fits exactly.

### Architecture

```
enthusiasticgeek/kosh-index   (public GitHub repo)
  config.json                 ← { "dl": "...", "api": "..." }
  <2-char prefix>/<pkg-name>  ← one JSON line per version
                                 (Cargo sparse format)

GitHub Pages: https://enthusiasticgeek.github.io/kosh-index/
→ vani.toml: source = "registry+https://enthusiasticgeek.github.io/kosh-index/"
```

Package tarballs are uploaded as GitHub Release assets on each
package's own repo. The index file records the download URL +
`sha256` checksum for reproducible builds.

### Q1. Hosting model — DECIDED

**GitHub Pages sparse index** (Cargo RFC 2789 format).
- Index: static JSON files in `enthusiasticgeek/kosh-index`,
  served free via GitHub Pages.
- Tarballs: GitHub Release assets (free for public repos).
- `vanic publish` = build tarball → upload Release asset →
  append version line to index file → push index repo.
- Migration path if GitHub Pages ever limits traffic: change
  one URL in `config.json`; format is identical everywhere.

Rejected alternatives:
- Git-based (Go modules): no search, no checksums, no
  `vanic add` metadata.
- HTTP+index (crates.io-style): needs a hosted server, has a
  running cost.
- IPFS: free but tooling is immature; overkill for 0 users.

### Q2. Authority — who owns the namespace? — DECIDED

First-come first-served on package names, enforced by the
index repo's CODEOWNERS / branch protection. The index repo
owner (`enthusiasticgeek`) is the sole write authority in v1.
No cryptographic signing required at this scale; SHA-256
checksums in the lockfile are sufficient tamper-evidence.

Org-namespaced packages (`@enthusiasticgeek/foo`) are
supported in the index file format (the path becomes
`en/enthusiasticgeek-foo`) but not enforced in v1.

### Q3. License + audit policy — DECIDED (v1)

No policy mandated at v1. Packages are flagged in the index
as `"verified": true` if every exported item carries a
`requires` / `ensures` contract that discharges under Z3.
Unverified packages are allowed; the flag is informational.

### Q4. Mirror policy — DECIDED (v1)

The index repo is a public git repo — anyone can fork it as
a mirror. `vani.toml` accepts any `registry+<url>` source, so
private / mirror registries work without compiler changes.
