# vāṇी v0.9.3 — 2026-08-12

Patch release. Consolidates 6 bug fixes (BUG-179 through BUG-184) since
v0.9.2 (2026-08-11), most of them a connected series in the SMT-based
bounds/overflow-elision pass shared by every backend, plus a tutorial
documentation pass and a new local QEMU cross-compile testing tool.

## Highlights

- **A three-bug soundness series in the SMT bounds-elision pass
  (BUG-181/182/183)**: found back-to-back via `tools/localfuzz` and a
  follow-up targeted audit. All three share the same root cause —
  `smt_facts`, the running list of "facts assumed true at this program
  point," going stale across a loop or branch boundary and letting the
  bounds-check elision logic "prove" an out-of-range index in-bounds. The
  worst of the three (BUG-181) was an unconditional, always-reachable
  out-of-bounds memory access: a SIGSEGV on the C backend, and silent
  unbounded out-of-bounds heap reads (no crash, no trap, just garbage
  values) on LLVM. All three are now fixed; see "Bug fixes" below for the
  full chain. The fix trades away a narrow, previously-real performance
  optimization (bounds-check elision on an index that's provably safe
  *inside a loop body*) for soundness — documented as a permanent,
  intentional limitation in `docs/v1_limitations.md`'s new **L26**, with
  cross-references from the SMT tutorial chapters so it isn't a silent
  surprise.
- **BUG-179/180**: two independent gaps found while writing tutorial
  coverage for previously-undocumented builtins — a `bptr_new`-without-
  `bptr_get` program crashing outright, and any explicit generic type
  annotation on a `let` inside an `unsafe`/`task` block failing to
  resolve regardless of what it named.
- **Local RISC-V/AArch64 QEMU testing**: `tools/install-cross-qemu.sh`
  installs and verifies the cross-compiler + QEMU toolchain needed to
  actually run cross-compiled `vanic` output on this kind of dev machine,
  alongside a new RISC-V/RVV specifics section in the SIMD tutorial.

## Bug fixes, by theme

### SMT bounds-elision soundness — BUG-181, BUG-182, BUG-183 (2026-08-12)

**BUG-181**: `try_elide_bounds_in_typed_expr`'s Index-elision arm didn't
guard against `smt_facts` staleness inside a loop body the way the
sibling arithmetic-overflow-elision arm already did (fixed earlier for
BUG-127) — a fact true only on a loop's first iteration (e.g. `j == 0`)
got used to "prove" a loop-mutated index always in-bounds for *every*
iteration, unconditionally eliding the runtime bounds check for the
entire loop. Confirmed to segfault outright on the C backend (raw
negative-index pointer arithmetic, no trap engaged) and to silently read
arbitrary out-of-bounds heap memory forever on the LLVM backend. Fixed
with the identical guard the overflow-elision arm already had; the
accepted trade-off is that a `for` loop's own otherwise-safe induction-
variable indexing now also keeps its runtime bounds check (a performance
regression, not a correctness one — see L26 below).

**BUG-182**: a sibling bug, found in the same localfuzz batch — this one
at a loop's *exit* rather than its interior. The post-loop fact restore
(`*smt_facts = pre_facts;`) reverts to a snapshot from *before* the loop
ran, still containing facts about any variable the loop body reassigned
(e.g. `len(xs) == 1` from before a loop that grows `xs` via `push`).
Combined with the loop's own freshly-added, correct post-loop facts
(its declared `invariant` plus the loop-exit condition), this produced
an internally contradictory fact set — from which the SMT solver can
"prove" anything, confirmed to elide a bounds check on a wildly
out-of-range constant index used *after* a loop, not even inside one.
Fixed by dropping every fact mentioning a loop-body-mutated variable
right after the restore, at all four loop constructs sharing this exact
pattern (`while`, `for`, `for`-iter, and the `let x = while ... {};`
loop-expression form).

**BUG-183**: a follow-up targeted audit (filed as
`docs/BUG_PATTERN_AUDIT_TODO_12.md` specifically to hunt this bug class)
found the identical stale-fact shape at four more merge points besides
loop exits: `if`/`else`, `if let`, the `select`-statement's internal loop
desugar, and `while let` — the last of which turned out to have no
fact-restore mechanism *at all*, so a pre-loop fact just sat there
unconditionally true forever regardless of what the loop body did. A
second, independent leak source also surfaced at two of these sites:
`env`'s own constant-tracking (read directly by the elision pass on
every query, bypassing the `smt_facts` list entirely) wasn't being
invalidated either, so fixing the fact list alone wasn't sufficient
there. All five gaps fixed using the same drop/clear pattern BUG-182
established.

### Other fixes

- **BUG-179**: `bptr_new` + `bptr_len` with no `bptr_get` call anywhere
  crashed both backends — the `Option<i64>` enum type both backends'
  `bptr_get` helper unconditionally referenced was only ever registered
  when `bptr_get` was actually called somewhere in the program, unlike
  every other `Option`-returning collection-helper family.
- **BUG-180**: an explicit generic type annotation (`Option<i64>`,
  `Result<T,E>`, or any user generic struct/enum) on a `let` inside an
  `unsafe(...) { }` block or a `task { }` spawn block never resolved —
  the monomorphization-instantiation walker had no case for recursing
  into either construct's body, unlike every other nested-block
  statement.
- **BUG-184**: `--big-o`'s complexity-classification pass listed a typo'd
  `btreemap_contains` (real builtin: `btreemap_contains_key`) and two
  builtins that don't exist at all (`btreeset_get`, `bst_search`),
  silently misclassifying real `BTreeMap`/`Bst` lookups as O(1) instead
  of O(log n). Advisory-annotation-only — never affected compiled code,
  found while adding regression coverage for paths the existing test
  suite never exercised.

## Tooling

- **`tools/install-cross-qemu.sh`**: installs `qemu-user-static` plus the
  AArch64/RISC-V64 cross-compiler toolchains on this machine's Debian/
  Ubuntu-family setup, verifies `binfmt_misc` registration directly
  against `/proc/sys/fs/binfmt_misc/` (not the legacy `update-binfmts`
  tool, which misreports on systems using the modern `systemd-binfmt`
  registration path), and prints ready-to-use `vanic run --target=`
  invocations for both architectures including RVV/SVE2-specific QEMU CPU
  flags. Supports a `--check`-only verify mode that needs no `sudo`.
- **`scripts/release.py`** now refuses to tag a release while
  `RELEASE_NOTES/v<ver>.md` or `CHANGELOG.md`'s own entry still hold
  unfilled scaffold placeholders — the exact gap that let v0.9.2 ship
  with untouched `TODO` stubs in both files. Override with
  `--allow-stale-notes` for genuine edge cases; `--dry-run` skips the
  check (files aren't necessarily written in that mode).

## Upgrade notes

- No breaking changes.
- **Performance, not correctness**: code that indexes a `Vec`/array
  *inside a loop body* no longer has that bounds check elided, even when
  it's actually safe (e.g. a `for` loop's own induction variable). This
  is BUG-181's permanent fix, documented as `docs/v1_limitations.md`'s
  **L26**. Straight-line code outside loop bodies (the common case —
  a `requires`-guarded function body, for example) is unaffected.
