# vāṇी v0.9.0 — 2026-07-26

A feature release: ref-capturing closures can now be passed around as
real first-class `Closure` values, not just called directly by name in
their own scope, with genuine non-escape enforcement rather than a
missing check. Alongside that: eight real compiler bugs found and fixed
(BUG-5 through BUG-12), most discovered by direct testing while building
the `vani-ml` and `vani-optimize` Kosh packages.

## What's new

- **Ref-capturing closures are now real values.** A `[ref name]`-capturing
  closure (shipped earlier, but previously only usable as a same-scope
  call-by-name shorthand) can now be passed as an argument to a
  `Closure(...)->...`-typed higher-order function parameter and produces
  the correct result, on both backends.
- **Non-escape enforcement for ref-capturing closures.** Returning one, or
  storing one in an outer-scope `Vec<Closure(...)->...>`, is now rejected
  at compile time with a clear diagnostic — the same class of protection
  already applied to plain `ref` locals.
- `vani-optimize` (Kosh package) gained `Closure`-accepting variants of
  its gradient-descent functions, additive alongside the originals — lets
  an objective function capture data (e.g. a training set) by reference
  instead of needing it as a global.

## Bug fixes

- BUG-5 / L25: `print`/`f64_to_str` scientific-notation exponent width
  differed between the C and LLVM backends on Windows.
- BUG-6: a standalone unary-minus float literal (e.g. `-3.0` as a bare
  call argument) panicked the LLVM backend at codegen, even though
  `vanic check` accepted it.
- BUG-7: the scope-escape analyzer missed a struct-with-ref-field
  escaping through an intermediate `let` binding — a real, confirmed
  dangling reference, not just a late diagnostic.
- BUG-8 (LLVM backend only): indexing through a `ref`-typed `Vec` struct
  field silently read garbage — the field's own struct address was used
  one pointer level too shallow.
- BUG-9: the `FieldAssign` scope-escape check could be fooled when the
  assignment target was reached through a `ref`/`mut ref` parameter
  rather than an owned local.
- BUG-10: a function merely *taking* a `Closure(...)->...`-typed
  parameter failed to compile unless some closure literal elsewhere in
  the same program happened to construct that exact shape.
- BUG-11 (C backend only): a closure shape referencing a `Vec<T>` could
  have its struct typedef ordered before `Vec<T>`'s own.
- BUG-12: the `push()` scope-escape check had the identical flaw BUG-9
  fixed for `FieldAssign`, for the same reason.

All eight fixes carry regression tests that actually execute the
compiled program (via `lli` or a compile-then-run check), not just
type-check it — several of these bugs specifically slipped through
because the pre-existing test for that shape only ever called the
type-checker.

## Upgrade notes

- No breaking changes. All new closure capability is purely additive;
  existing code is unaffected.
- If you maintain a Kosh package with a `fn(ref Vec<f64>, i64) -> ...`-
  style objective/gradient parameter (the convention `vani-optimize` and
  `vani-interval` use), consider adding a `Closure`-accepting variant
  alongside it — see `vani-optimize`'s `gradient_descent_fixed_closure`
  for the pattern, and `docs/ref_capturing_closures_design.md` for the
  full design writeup.
