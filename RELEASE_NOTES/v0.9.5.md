# vāṇी v0.9.5 — 2026-08-24

Consolidates 21 bug fixes (BUG-202 through BUG-227) plus three
long-standing limitations closed (L29 fully, L32) since v0.9.4
(2026-08-17), alongside a real feature: `step N` (a stride other than
1 for range-form `for` loops), a mechanical audit tool
(`vanic coverage-gaps`), and a full 90-file tutorial accuracy audit
that added a missing beginner capstone chapter. See
`docs/TODO_CURRENT.md` for full per-bug detail; this file groups by
theme. Two consecutive sibling-sweep sessions this window (2026-08-17
and 2026-08-21/23) each found 4+ real bugs by deliberately auditing
related functions/features after fixing the bug that triggered the
audit, rather than stopping once the triggering repro passed — that
practice, not any single fix, is the biggest theme of this release.

## Highlights

- **`step N` closes L29 completely**: `for i from 0 to 20 step 3`
  (and its `downto` counterpart) names a stride other than 1 —
  `downto` itself shipped in v0.9.3's window, `step` was the
  remaining gap. Ships with the same full-scope treatment as
  `downto`: a hard compile-time error for a known non-positive
  constant step, a clean runtime trap for a non-constant one, and —
  matching the `downto` precedent exactly — the same-day 62-dialect
  keyword-parity sweep (not English-only). `#[wcet(cycles=N)]`'s
  static trip-count formula now does ceiling division by `step`.
  Sequential loops only for now (rejected on `parallel for` at parse
  time, same scoping `downto` already has).
- **Sibling-sweep sessions found the majority of this release's real
  bugs**: two multi-bug sessions (2026-08-17: BUG-202 through
  BUG-213; 2026-08-21/23: BUG-215 through BUG-219) each started from
  one localfuzz or coverage-tooling finding, fixed it, then
  deliberately audited every function/feature sharing the same shape
  before moving on. That discipline directly found BUG-206/207/208/
  209 (four *additional* bugs in one day, none independently
  reported) and a real memory-safety bug (BUG-215, below) that a
  narrower "fix and stop" pass would have missed.
- **A real, exploitable heap-corruption bug** (BUG-215): `UnionFind`'s
  `find(x)` silently returned an out-of-range `x` unchanged instead
  of trapping — the *only* bounds-checked builtin in the compiler
  that did this instead of exiting cleanly — letting a caller's
  `union(a, b)` use the unvalidated result as a raw array index and
  perform an out-of-bounds heap write. Surfaced downstream as a
  confusing `free(): invalid pointer` (C) or JIT segfault (LLVM), far
  from the actual defect. A follow-up sweep confirmed this was the
  *only* instance of the shape in the codebase (`Graph`, `BoundedPtr`,
  `Trie`/`Bst`/`SkipList` all checked clean).
- **A soundness-hole family in the SMT verifier** (BUG-208/210/211/
  212/213): a `mut ref` call to a user function, a `mut ref` builtin
  call, and ordinary branch-merge/reassignment could each leave a
  *stale* fact in the checker's model after the state it described
  had actually changed — in the worst cases (BUG-208, BUG-212) letting
  `prove`/`requires`/`ensures` accept claims that are actually false,
  not just fail to prove true ones. All four caches (`smt_facts`,
  `struct_literal_fields`/`.constant`, `vec_literal_elements`, the
  array-version counter) were consolidated into one
  `invalidate_facts_on_opaque_mutation()` method, which itself then
  found two *more* real gaps (branch-merge, reassignment) the
  patchwork fixes hadn't covered.
- **Full 90-file tutorial accuracy audit**: every "here's the real
  compiler output" code block, cross-file claim, and CLI/attribute
  name across the entire tutorial book was spot-verified against a
  current build, not just proofread. Found and fixed several stale
  claims (a false "`Option<T>` is i64/f64-only" restriction, a false
  "no `Box<T>`" claim contradicting the language's own Box+RAII
  primer, two nonexistent attribute spellings the compiler actually
  rejects) plus navigation/banner bugs. Added a missing capstone —
  the beginner track was the only one of the three with none.
- **`vanic coverage-gaps`**: a new mechanical hypothesis generator for
  audit rounds, answering "would coverage scoring help find bugs
  faster?" — it can't confirm a gap on its own, but it can rank
  candidate feature-combination gaps by how under-exercised they are
  in the existing corpus, cutting down the manual search space before
  hand-writing a candidate program. Wired into localfuzz too.

## Bug fixes, by theme

### Vec/Array LLVM-backend bugs (BUG-202, BUG-203, BUG-204, BUG-206)

Found writing a real test for a previously-untested vani-ml function,
which hit two independent, previously-undiscovered `Vec<bool>`
LLVM-backend bugs, then two more via the sibling-sweep practice above:

- **BUG-202** (crash): `Vec<bool>`'s packed-bit layout tracks capacity
  in BITS everywhere except its own literal/empty constructors, which
  computed it as an ELEMENT count — the very next `push` past the
  undersized capacity divided by 64 with no rounding, computed a
  0-byte `realloc`, and dereferenced the resulting null/invalid
  pointer.
- **BUG-203** (silent corruption, found immediately after fixing
  BUG-202 let the test run far enough to hit it): the bit-OR insert
  logic used LLVM `sext` (sign-extend) on a boolean instead of `zext`
  — `sext`-ing `true` produces all-ones (`-1i64`), which, shifted into
  position, sets every higher bit in the same 64-bit word, silently
  corrupting every later element the instant any element is pushed or
  set `true`.
- **BUG-204**: the generic (non-bool) `set`/`set_mut` LLVM helpers had
  **no bounds check at all**, unlike every other Vec accessor in the
  same file — an out-of-range index corrupted the heap and segfaulted
  instead of exiting cleanly (the C backend was already correct here).
- **BUG-206**: `vec_swap` had no bounds check on *either* index, on
  **both** backends — the 7th bug in a recurring missing-bounds-check
  family (BUG-108, 120, 147, 148, 149, 204, now 206) across many
  sessions, each previously fixed narrowly for the one function that
  triggered it rather than the whole accessor family.

### `ctx.current_block` LLVM-backend staleness (BUG-207)

The same recurring bug class as v0.9.4's BUG-185/196: both
`TypedStmt::For` and `TypedStmt::ForIter` never updated
`ctx.current_block` anywhere in their own codegen (header, body, step,
or exit blocks), so any later phi-node-consuming construct in the same
function captured the wrong predecessor and `lli` rejected the module.

### SMT stale-fact soundness, the `VarInfo`-cache family (BUG-208, BUG-210, BUG-211, BUG-212, BUG-213)

Direct continuations of v0.9.4's BUG-198/199 series — a `VarInfo`
cache going stale after the state it described changed:

- **BUG-208**: a `mut ref` call to a *user-defined* function mutating
  a struct field never invalidated the caller's stale
  `struct_literal_fields`/`.constant` facts (only a *direct*
  `obj.field = value;` did) — a real path to `prove` accepting a false
  claim, not merely missing an optimization.
- **BUG-210**: a `mut ref` *builtin* call (`set(mut ref xs, ...)`)
  left a stale `vec_literal_elements` cache in place, letting
  compile-time index substitution silently use the array's *original*
  construction-time value after it had been mutated.
- **BUG-211**: the same mut-ref-call gap for the SMT array-versioning
  counter itself — a 4th distinct stale-cache shape at the identical
  call site.
- **BUG-212**: `clear_constants_for` (used by every `if`/`while`/`for`
  branch-merge in the language, 6 call sites) only ever cleared
  `.constant`, not the other three caches above — despite its own doc
  comment already listing `mut ref` mutation as a case it's supposed
  to cover. Substantially larger blast radius than 208/210/211
  combined, since branch merges are pervasive.
- **BUG-213**: `Stmt::Reassign` (`xs = <new value>;`) had the identical
  gap — a complete reassignment to a brand-new literal still left
  stale facts about the *original* value in place.

All five consolidated into one `invalidate_facts_on_opaque_mutation()`
method on `VarInfo`, replacing four separate patchwork call sites.

### `parallel for` reduction overflow gaps (BUG-214 C backend, BUG-222/BUG-222-followup LLVM backend)

`reduce <var> with +/*;` on an integer type has a checked-arithmetic
gap at the point where the parallel runtime combines each thread's
own (individually valid) partial sum into the final total — a step
this compiler's own instructions never see:

- **BUG-214**: the C backend lowers `reduce` to an OpenMP
  `reduction()` clause; libgomp's own final combine step is invisible
  to this compiler and had no overflow check at all, silently
  wrapping. Fixed by falling back to a sequential loop specifically
  for integer `+`/`*` reductions (the only ops where the *combine*
  itself can overflow), keeping every other reduction shape
  parallelized.
- **BUG-222** (LLVM, both the SSA and tree backends independently):
  the same shape in LLVM's own manually-outlined pthread-pool
  reduction combine, which used a plain `atomicrmw add` with no
  overflow check for the `Add` case (the `Mul` case already used a
  checked CAS-retry loop). Fixed by routing `Add` through the same
  checked-CAS pattern `Mul` already used.

### Other correctness fixes

- **BUG-215**: `UnionFind.find()` heap corruption — see Highlights
  above.
- **BUG-209**: `lex_ident` (the ASCII-identifier lexer used by every
  Latin-script dialect) never got BUG-175's mid-word-apostrophe fix,
  which only landed in the separate `lex_unicode_ident` function.
  French `l'arbre` (a completely ordinary elision) failed to parse.
- **BUG-216, BUG-217, BUG-218**: a feature-combination audit round
  (deliberately combining recently-touched features, e.g.
  `cancel`+`Task<R>`, `cancel`+`detach`, `downto`+`parallel`) found a
  `Vec<T>` heap-corruption-and-leak bug for level-4 builtin types
  (BUG-216), which a follow-up sibling sweep of every RAII type then
  found two more instances of in `Box`/`Region` (BUG-217), plus a
  `Mutex`/`Guard`/`RwLock` SSA-LLVM naming mismatch and a real
  `Mutex<NonCopyT>` double-free soundness gap (BUG-218).
- **BUG-219**: a duplicate `reduce total with +; reduce total with +;`
  clause for the *same* variable reached codegen instead of being
  rejected — the checker already built a `HashSet` clearly intended
  for exactly this duplicate check, but its result was discarded and
  the whole set thrown away right after. LLVM rejected the resulting
  IR outright; the C/OpenMP backend silently accepted it with
  unspecified behavior (which clause's partial "wins").
- **BUG-220**: struct-literal arity errors (`Point { x: 3 }` against a
  2-field struct) reused function-call-argument-count help text
  verbatim ("update the function's signature" — there is no
  function). Given a dedicated, struct-literal-specific elaboration.
- **BUG-223**: moving a heap-owning field (`OwnedStr`/`Box<T>`/`Vec<T>`)
  *out* of a `ref`/`mut ref` struct parameter was accepted by the
  affine checker but produced a double-free at runtime — the borrow
  doesn't own the struct, so it can't legally consume one of its
  fields either. Now a compile-time error.
- **BUG-224**: `extern "C" fn ... -> Str` declarations always spelled
  the return type `const char*` on both C backends, conflicting with
  real libc headers whose own signature isn't `const`-qualified
  (`getenv`, `strdup`, confirmed against `stdlib.h`/`string.h`). Fixed
  generally (not by extending an existing narrow allowlist) by
  emitting plain `char*` for any `extern "C"` function returning
  `Str`.
- **BUG-226**: bare `vanic test` (the package-root default, used by
  every Kosh package's own test suite) reported the package's own
  `src/lib.vani` — which has neither `#[test]` functions nor `fn
  main` — as a spurious "failed" test on every run, purely by
  elimination in the file-discovery logic's fallback case. Affected
  essentially the whole Kosh ecosystem's default `vanic test`
  invocation.
- **BUG-227**: full SMT verification (`vanic check`/`test` without
  `VANIC_NO_VERIFY=1`) hung indefinitely on several Kosh packages
  (`vani-symbolic`, `vani-ml`, and — found via re-testing after the
  fix — `vani-pde`, `vani-probability`). Two independent root causes:
  the checker forwarded every fact accumulated in a function to every
  later proof with no relevance filtering, so one expensive `f64`
  division got re-solved by Z3 on every unrelated subsequent proof in
  the same function; and the SMT query cache (keyed on exact query
  text) was silently defeated by non-deterministic `HashSet`
  iteration order across `vanic test`'s worker threads, forcing every
  shared library function to be re-verified once per thread instead
  of once total.
- **L32**: `नियोग<T>` (`Task<R>`'s Devanagari spelling) couldn't be
  used as an explicit type annotation — Devanagari has no case
  distinction, so it always lexed to the reserved `Task` keyword
  token instead of falling through to a plain identifier the way
  ASCII `Task` does. `parse_type` now recognizes a bare `Task` token
  directly, with the same `<`-lookahead disambiguation the
  `Ident("Task")` path already used.

## Tooling

- **`vanic check --coverage`**: feature-combination coverage scoring
  against the example corpus, the confirmation half of the audit
  workflow `vanic coverage-gaps` (above) now feeds candidates into.
- **`tools/localfuzz`**: two triage-ergonomics fixes. The digest
  generator can now tell "matched a bug mention, might need
  re-verification" apart from "matched, but a human already decided
  this is intentional and permanent" (a `KNOWN_ACCEPTED` table
  collapses the latter to one line instead of re-flagging on every
  run — cut ~30% of one round's findings-needing-triage down to a
  single line each). The fuzzer's numeric-boundary mutator no longer
  inserts `i64::MIN`/`i64::MAX` into `sleep_ms(...)` calls or loop
  bounds specifically, cutting down "correctly asking for 9.2
  quintillion iterations, not a bug" false-positive findings (~24% of
  one round).
- **`vanic publish`**: the published tarball now also carries native
  FFI shim sources (`.c`/`.h`/`.cu`/`.cuh`/`.cpp`/`.hpp`), not just
  `.vani` files — needed for Kosh packages that ship a real C/CUDA
  shim alongside their vāṇी bindings.

## Upgrade notes

- **New reserved word**: `step` is now a keyword (and its translation
  in every dialect that already has `to`/`downto` — see
  `docs/archive/grammar_review_queue.md`'s "step keyword-parity
  sweep" table). An identifier literally named `step` in existing
  source will need renaming; confirmed via a corpus-wide sweep that
  exactly one example file in this repository used it as a variable
  name (renamed to `stride`).
- No other breaking changes.
